# AgentCP V3：安全研究 Agent 的工程化设计与实现

项目地址：[https://github.com/feifei-gongzhu/AgentCP](https://github.com/feifei-gongzhu/AgentCP)

参考资料：[《面向客户端漏洞挖掘 Agent 的设计与实践之路》](https://mp.weixin.qq.com/s/7r5nK1JlQr6pD3AOVfuG1g)

AgentCP 是一套面向授权安全研究的多 Agent 控制系统。用户通过 Web 控制台创建任务、填写目标、选择 Web 或客户端场景、配置模型团队并启动运行。后端负责拆分研究方向、并发调度执行、保存工具证据、判断结果成熟度，并在关键节点交回人工控制。

它和普通聊天式安全助手的区别在于：系统输出的不是一段“可能存在某漏洞”的回答，而是一个可持续运行的项目。资产、假设、任务、失败路径、原始证据、漏洞候选和人工结论都会持久化，服务中断后仍可恢复。

本文介绍 AgentCP 从单 Agent Profile 到 V3 控制平面的演进，以及当前各部分的设计取舍。

## 一、从单 Agent 开始的两次尝试

AgentCP 的早期形态是两份 Claude Profile。

### 1.1 V2.0：先解决长任务失忆

`claudeV2.0.md` 引入了一块双层项目黑板：文件顶部是 YAML 控制摘要，下面是 Markdown 研究记录。目标信息、动态检查清单、项目黑板和决策日志分别保存在项目目录中。

这一版本还有两个明确要求：

- 每个发现都要说明可能造成的业务损失，避免长期停留在低价值资产信息上；
- 完成一个子任务或同一路径达到 15 分钟后，暂停当前工作，向用户报告投入、产出和下一步选择。

它解决了对话关闭后信息丢失的问题，也形成了后来 AgentCP 的控制层、工作层和人工门禁。

### 1.2 V3.2：开始处理不确定性

`claudeV3.2.md` 主要增加了四项设计：

| 设计 | 目的 |
|---|---|
| Phase 0.5 探针 | 在高成本逆向或动态调试前，先用低成本手段判断目标是否值得投入 |
| 三级判断 | 将结果分为可推进、不可推进和条件不充分，避免二元结论 |
| 探索预算 | 给低概率但高影响的直觉方向预留固定时间 |
| 反事实与经验失效条件 | 放弃路径时记录可能遗漏的证据，避免历史经验永久影响新项目 |

这些方法继续保留在 V3 中，但原来的执行方式被放弃了。原因是所有职责仍集中在同一个 Agent：它选择方向、执行工具、评价结果、计算预算并监督自己停止。

当上下文变长后，控制规则会和工具输出竞争注意力。Agent 也容易继续维护自己刚刚作出的判断。单 Agent 可以写出完整流程，却无法为自己的状态和结论提供独立约束。

V3 的改造原则由此确定：研究判断可以交给模型，项目状态不能交给模型自觉维护。

## 二、Agent 方案选型

### 2.1 为什么不是一次模型调用

漏洞研究不是一个输入对应一个答案的任务。初始目标通常只提供很少的信息，需要先形成观察，再根据观察决定下一步动作。

例如，一个静态资源中出现新的接口域名后，后续可能转向接口结构、身份边界或业务对象；一个本地服务被确认后，研究方向可能转向调用者身份、协议解析或高权限消费方。路径取决于中间结果，无法在开始前完整写成固定流程。

AgentCP 的 Worker 因此以循环方式工作：读取当前项目状态，判断最需要补充的证据，执行一个有明确边界的动作，再将观察结果交回系统。ReAct、OODA 或 Loop Engineering 使用的名词不同，关键都在于让中间观察真正改变下一轮规划。

对安全研究而言，最终效果主要受四项因素共同影响：

```text
有效产出 ≈ 方向质量 × 工具真实性 × 证据可信度 × 调度效率
```

模型只负责其中的方向质量。工具没有真实执行、证据无法复核或者多个 Worker 重复工作时，单纯更换更强模型不会解决整体问题。

### 2.2 Worker 如何划分

AgentCP 将模型角色拆成四类：

| 角色 | 处理的问题 | 不具备的权限 |
|---|---|---|
| Reason | 当前最值得验证的假设是什么 | 不能直接把假设写成漏洞 |
| Metacog | 主规划遗漏了什么、哪条结论可能错误 | 不能绕过调度器强制执行 |
| Executor | 如何完成具体动作并留下原始结果 | 不能自行确认漏洞成立 |
| Reviewer | 证据与结论是否一致 | 不能替代 Guardian 和人工裁决 |

模型之外还有 Scheduler、Controller、Guardian 和 Store。它们使用普通代码处理任务租约、状态转换、结果分类和事务写入。

这种拆分不是为了增加角色数量，而是让提出方向、执行验证和修改项目状态分别受到不同约束。

### 2.3 执行环境

AgentCP 支持两类目标环境：

| 执行环境 | 适合任务 |
|---|---|
| Host / Workspace Worker | 需要访问本地源码、客户端文件、宿主工具或调试环境的任务 |
| Container / Sandbox Worker | 解包、字符串分析、静态扫描及适合隔离执行的工具任务 |

真实模型统一通过 agent-compose 启动。AgentCP 负责准备任务上下文和项目权限，agent-compose 负责模型进程、沙箱、会话和工具日志。

前端填写的模型、服务地址、认证方式和会话 API Key 会传入后端运行时。Key 只存在于当前服务进程内存，不写进项目配置、数据库、事件日志或页面响应。

### 2.4 记忆如何设计

安全研究中的记忆不能简单理解为“把历史对话放进向量库”。不同内容的读取者、有效期和使用方式都不同。

AgentCP 在设计记忆时分别处理四个问题：

| 问题 | AgentCP 的选择 |
|---|---|
| 谁使用 | Reason、Metacog、Executor、Reviewer 和用户共享同一项目状态 |
| 保存什么 | 原始结果进入 Evidence；经过分类的观察进入 Fact；未验证判断进入 Hypothesis |
| 保留多久 | 漏洞与人工结论长期保存；环境性失败设置有效期；短期运行信号保存在事件流 |
| 如何读取 | 按目标、阶段、假设关联和时间筛选，不把全部历史塞进上下文 |

单 Agent 会话只能保存当前推理轨迹。进程退出后难以恢复，多 Agent 也无法可靠共享。AgentCP 将状态放在模型外部，Worker 本身不承担长期记忆。

项目中同时使用几类存储：

- SQLite WAL 保存 Run、Wave、Job、租约、心跳和事件；
- JSONL 保存事实、方向、假设、反事实、Lesson 和人工裁决；
- evidence 目录保存原始请求响应、工具输出和文件哈希；
- 双层 Markdown 黑板提供给人阅读和干预。

原始数据与研究结论分开后，模型摘要不会覆盖真正的工具结果，用户也可以追溯每条结论从哪里产生。

### 2.5 多 Agent 如何协作

多 Agent 常见的组织方式各有适用范围：

| 方式 | 优点 | 在安全研究中的问题 |
|---|---|---|
| 固定流程 | 顺序清晰，容易测试 | 无法提前知道下一个有效入口在哪里 |
| 显式移交 | 角色边界明确 | 长链路中移交上下文成本高 |
| 自由群体 | 发散能力强，容易增加 Worker | 重复任务和状态冲突难以控制 |
| 黑板协作 | Worker 可异步读取同一事实集 | 需要额外解决去重、租约和全局可观测性 |

AgentCP 采用受控黑板协作。Worker 不直接私聊，只提交结构化候选；Scheduler 决定谁能认领任务；Guardian 决定候选可以进入哪一层；Controller 处理用户命令和运行状态。

研究方向可以动态变化，但状态转换必须由确定性代码完成。这是 AgentCP 与完全自由 Swarm 的主要区别。

### 2.6 为什么需要模型之外的质量门

模型很容易把“值得继续研究”写成“漏洞已经成立”。典型情况包括：

- 将开放端口或框架版本直接报告为高危；
- 把返回 401 的接口解释为鉴权漏洞；
- 根据静态配置推测一条攻击链，但没有执行验证；
- 声称结果已保存，实际证据文件不存在；
- 使用“可能造成接管”等影响描述代替真实边界变化。

如果这类结果直接进入共享黑板，后续 Worker 会把错误结论当成前置事实，规划和漏洞计数都会被污染。

因此 AgentCP 不让模型拥有最终分类权。所有候选先进入 Evidence Normalizer，再由 Guardian 使用确定性条件裁决。规则可以测试、回放和版本化，不依赖模型在长上下文中记住质量要求。

## 三、AgentCP V3 架构

### 3.1 黑板、调度器与 Worker

```text
                    Web 控制台
        项目配置 / 运行过程 / 人工干预 / 结果复核
                           │
                           ▼
                AgentCP API 与控制层
       Controller / Scheduler / Guardian / Store
              │             │             │
           SQLite       项目黑板      Evidence
              │
              ▼
                agent-compose 运行层
       Reason / Metacog / Executor / Reviewer
```

控制平面和执行平面分工如下：

| AgentCP 控制平面 | agent-compose 执行平面 |
|---|---|
| 项目、目标、方法包 | 模型进程与 Provider |
| 假设、Intent、证据索引 | 沙箱和会话 |
| Run、Wave、租约和停止 | 工具调用和日志 |
| Guardian 与人工审批 | 进程启动、复用和终止 |

agent-compose 在 V3 中是必需运行时。如果运行时没有构建成功，任务直接失败，不会静默退回宿主机直连 CLI，避免用户配置的隔离边界失效。

### 3.2 黑板数据模型

AgentCP 的黑板由八类核心对象组成：

| 对象 | 作用 |
|---|---|
| Fact | 已经观察到并完成分类的事实 |
| Hypothesis | 对某条安全边界的待验证判断 |
| Intent | Executor 可以认领的具体动作 |
| Evidence | 原始结果、文件路径和哈希索引 |
| Negative Evidence | 当前条件下失败或被阻断的路径 |
| Counterfactual | 能够推翻当前判断的条件 |
| Hint | 用户注入的方向和控制要求 |
| Human Verdict | 用户对漏洞候选的最终意见 |

基本流转关系为：

```text
Fact + Method Pack
        ↓
Hypothesis
        ↓
PlanBatch 选择
        ↓
Intent 被认领
        ↓
Executor 产生 Evidence
        ↓
Guardian 分类
        ↓
新 Fact / Negative Evidence / 漏洞候选
```

每条 Intent 都包含动作、目标、证据输出位置和成功条件。只写“继续看看该接口”不能进入任务队列。

### 3.3 调度生命周期

一次自动化运行称为 Run，一个 Run 可以包含多个 Wave。

```text
Run 创建
  ↓
Wave 1：Reason 与 Metacog 生成候选假设
  ↓
系统评分、去重并选择 PlanBatch
  ↓
Wave 2：Executor 并发执行选中 Intent
  ↓
Guardian 收敛结果并派生相邻方向
  ↓
Wave 3 / Wave 4：继续验证或复核
  ↓
达到时间、波次或门禁条件后暂停
```

当前单 Run 最多四波，并受总执行时间限制。Reason 在运行中产生的新方向可以进入下一波，不需要用户重新点击开始。

Executor 认领任务后获得租约，并持续上报心跳。租约过期后，任务可被释放和重新认领。每个 Job 记录 Worker、角色、模型、Wave、尝试次数、最后心跳和最近工具动作。

### 3.4 四项相互关联的设计

V3 的研究质量主要由四项机制共同保证：

1. Method Pack 规定应覆盖哪些边界；
2. PlanBatch 同时比较多个假设，减少单一路径锁定；
3. Guardian 将现象和漏洞分开；
4. 黑板与调度器为前三项提供共享状态和执行能力。

只有攻击面模型而没有真实 Intent，覆盖率会变成页面装饰；只有多个 Agent 而没有去重，它们会并发重复；只有质量 Prompt 而没有 Guardian，错误发现仍会污染黑板。

## 四、Method Pack：把检查思路变成可调度对象

### 4.1 Web 方法包

Web 项目初始化后生成十个基础研究维度：

| 维度 | 主要观察对象 |
|---|---|
| API 路由 | 路由、方法、对象标识、鉴权要求和响应结构 |
| 外网服务 | 端口、协议、服务指纹与 SSRF 可达边界 |
| 权限边界 | 对象级、功能级、租户级和身份级授权 |
| 目录与资产 | 主机、路径、静态资源和环境资产 |
| 框架与配置 | 框架指纹、调试、运维、文档和配置入口 |
| 输入解析 | 上传、转换、复杂格式和反序列化入口 |
| 三方组件 | 组件、版本、可达性和利用前置 |
| 凭据线索 | 静态资源、配置和公开数据中的凭据痕迹 |
| 云权限 | 对象存储、元数据、云身份和服务授权 |
| 业务流程 | 账户、资金、隐私、配额和状态机完整性 |

### 4.2 客户端方法包

客户端项目使用另一组维度：

| 维度 | 主要观察对象 |
|---|---|
| 本地通信 | IPC、RPC、Socket、WebSocket 和调用者身份 |
| 本地服务 | 监听地址、协议、进程归属和访问控制 |
| 提权路径 | 高权服务、助手程序和低权可控输入 |
| 文件信任 | 安装目录、配置、更新文件和 TOCTOU |
| WebView / Electron | preload、上下文隔离、原生能力和导航策略 |
| 解析器与 FFI | 文件格式、自定义协议、原生库和跨语言调用 |
| 更新与供应链 | 下载、签名、依赖、SDK 和构建信息 |
| 本地敏感数据 | 日志、缓存、配置、凭据和隐私数据 |
| 权限与沙箱 | 权限声明、沙箱例外和跨进程能力 |
| 外部入口 | 深链、文件关联、首装、升级和卸载残留 |

Method Pack 的每个维度不仅有名称，还包含目标、初始动作、完成条件、潜在影响和下一条相邻验证方向。

覆盖状态只能由 Fact 推进。模型不能自行宣布某个维度已经检查完成。

### 4.3 Web 与客户端为什么不能使用同一套规划

Web 黑盒研究的首要问题通常是未知：还有哪些主机、路由、服务和对象没有被发现。信息会随着探测逐步增加。

客户端研究往往在开始时已经拿到安装包或源码。大量入口可以直接从文件结构、配置、符号、权限和本地通信中观察到，主要问题从“发现入口”转为“覆盖入口并证明真实影响”。

| 对比项 | Web 黑盒 | 客户端 / 灰盒 |
|---|---|---|
| 初始信息 | 较少，需要逐步扩展 | 安装包或代码提供大量静态信息 |
| 规划重点 | 扩展资产并识别身份和业务对象 | 系统覆盖并追踪到真实调用边界 |
| 常见低质量结果 | 重复枚举、只记录指纹 | 把危险配置直接当作漏洞 |
| 关键指标 | 新信息增益与边界闭环 | 覆盖率、可达性和动态验证率 |

因此两类项目共享同一控制平面，但使用不同 Method Pack 和初始假设。

## 五、PlanBatch 与双 Agent 规划

### 5.1 为什么一次提交多个假设

早期 Reason 每轮只提交一个方向，容易在第一条合理路径上持续加码。V3 要求它一次给出 1～12 个候选假设，系统最多选择 5 个。

一个完整假设包括：目标、所属维度、需要验证的边界、执行方案、成功条件、证据位置、预期影响、信息增益、前置就绪度、预计成本和动作风险。

调度器根据这些字段重新计算优先级，并优先选择不同目标、不同维度的假设。这样可以减少多个 Executor 同时进行同类资产枚举。

潜在漏洞危害与验证动作风险分别计算。高影响假设可以使用低风险方式验证；高风险动作即使对应普通假设，也必须经过人工批准。

### 5.2 Reason 与 Metacog

Reason 负责在已有事实和方法包内收敛，Metacog 负责检查主策略所依赖的前提。

例如 Reason 判断“当前接口都由统一鉴权层保护”，Metacog 不能只回复“建议继续关注鉴权”，而要给出：

- 哪个目标可以进行对照；
- 改变哪个身份或对象变量；
- 结果保存到哪里；
- 什么差异能够推翻统一鉴权假设。

Metacog 的输出同样进入 PlanBatch，由系统评分和去重。它不会因为角色名称是“反思员”而获得更高调度优先级。

### 5.3 反事实

PlanBatch 可以附带结构化反事实，记录当前判断及其证伪条件。反事实与相关 Hypothesis 建立关联，并在后续规划中按需检索。

这使“反思”从一段不可执行的模型自评，变成能够触发后续验证的项目对象。

## 六、Guardian：区分攻击面、线索和漏洞

### 6.1 裁决依据

Guardian 不根据严重性措辞和单个 HTTP 状态码判断漏洞。候选要进入漏洞池，需要同时满足两类条件。

**边界证据**

- 测试身份获得原本不具备的能力；
- 实际读取不应访问的敏感数据；
- 安全控制被稳定绕过；
- 受保护对象受到可验证影响。

**复核证据**

- 结果可以重复；
- 原始请求响应或工具输出已经保存；
- 证据文件存在且非空；
- 文件哈希和索引一致；
- 结论与实际观察相符。

401、302、403 或 200 只能作为观察的一部分。状态码本身既不能证明漏洞，也不能直接排除漏洞。

### 6.2 四级分类

| 分类 | 含义 | 是否增加漏洞计数 |
|---|---|---|
| 漏洞候选 | 边界已经突破，证据可复核 | 是，等待人工裁决 |
| 风险线索 | 已有异常或价值信号，但没有形成完整边界闭环 | 否 |
| 攻击面 | 只确认资产、入口、服务、组件或配置 | 否 |
| 无结论 / 负向证据 | 验证失败、超时、阻断或证据不足 | 否 |

Guardian 只能将模型候选降级，不能从普通攻击面主动生成漏洞。被降级的记录不会删除，后续获得新证据后仍可重新验证。

## 七、失败路径与 WAF

### 7.1 Negative Evidence

失败结果包含目标、假设、方法、失败原因、观察时间、有效期、网络环境、尝试次数和重新验证条件。

只有目标、假设、方法和环境一致，记录仍在有效期内，并且没有触发失效条件时，Scheduler 才拒绝重复调度。

IP、网络出口、身份变化或用户强制复测都会使旧结论失效。这样既减少重复工作，也不会把一次临时失败变成永久黑名单。

### 7.2 WAF 评估分支

WAF 命中不会直接结束整个研究方向。系统先建立请求基线，再在受限预算内逐轮改变单一变量，观察状态、长度、响应头和耗时是否形成稳定差异。

有稳定差异时生成新的验证假设；没有差异且预算耗尽时，将当前环境下的阻断结果写入 Negative Evidence。

WAF 分支有独立的时间和尝试上限，避免 Worker 长期停留在同一防御机制上。

## 八、控制器与并发一致性

### 8.1 stop_loss 的优先级

用户停止 Run 后，仍可能有 Worker 在网络请求或模型调用中。旧任务返回时不能修改已经停止的项目状态。

AgentCP 使用控制版本隔离迟到写回：

```text
Worker 领取任务：control_version = 21
用户执行止损：control_version = 22
旧 Worker 返回：21 != 22
Store 拒绝写回
```

止损过程会停止活动进程和沙箱，回收已认领 Intent，并将 Run 写入终结态。自动继续逻辑无权覆盖该状态。

### 8.2 用户指令

人工 Hint、方向删除、继续运行、止损和漏洞裁决都通过控制 API 写入，并记录作用项目、Run 和时间。

用户指令优先于模型建议。模型可以在下一轮读取并解释 Hint，但不能判断这条用户指令是否“适用于当前策略”后自行忽略。

### 8.3 阶段状态机

项目阶段由持久化结果计算：

```text
目标接入 → 初步探测 → 资产侦察 → 假设研究 → 漏洞验证 → 报告复核
```

除非目标被清空，阶段只向前推进。模型输出中的阶段描述不会直接修改状态。

## 九、过程可观测性

“调度心跳正常”只能说明 Worker 租约仍然存在，不代表模型正在产生新结果。

AgentCP 将运行信号分开显示：

| 信号 | 用途 |
|---|---|
| 调度心跳 | 判断 Worker 和租约是否存活 |
| agent-compose 状态 | 判断会话、沙箱和 Run 生命周期 |
| 模型工具事件 | 展示最近执行的真实工具动作 |
| Evidence 状态 | 判断结果是否已经落盘并完成哈希 |
| Guardian 事件 | 展示候选被接受或降级的原因 |

前端任务行显示当前角色、研究目标、成功条件、模型、Wave、尝试次数、最近工具动作、已等待时间和最近错误。

用户需要能够直接判断：当前是谁在执行、执行到哪一步、没有结果是因为模型等待、工具阻塞、任务重试还是证据未通过。

## 十、人工裁决与长期质量指标

通过 Guardian 的结果进入系统漏洞池后，用户可以：

- 认可系统判断；
- 调整漏洞等级；
- 驳斥为误报；
- 降级为风险线索或攻击面；
- 补充条件并要求复测。

机器原判和人工结论分别保存。任务中心长期统计已审数量、确认率、误报率、等级高估率、低估率以及不同 Guardian 版本的表现。

人工驳斥理由还会进入反例记忆。相同模式多次出现时，系统生成 Guardian 规则候选，但不会自动启用。候选需要先在历史证据上回放，再由用户批准，避免为了降低一种误报而引入新的漏报。
