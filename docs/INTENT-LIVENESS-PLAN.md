# 孤儿意图对账施工方案

依据 01 号文件第六、十一、十二、十四至十七章。原件保持只读。程序从持久执行记录推导意图运行状态、记录可恢复现场和搁置条件。Orchestrator 选择继续、换执行者、换方向或请求重规划。

[PentestGPT §5.3](https://arxiv.org/html/2308.06782v2) 的任务树提供进展记录和选择下一步的结构。[MemWalker §3](https://arxiv.org/html/2310.05029v1) 的返回父节点是模型可选的阅读动作。事务对账、重试上限和执行分支回溯是 Sorne 依据 01 号文件采用的工程设计。Goal 层级提供阅读与调度入口，跨分支依赖仍由关系记录表达。

## 1. 明确执行态与收尾原因

在每个受控写事务提交后，`running` 意图必须拥有至少一个有效活跃 Attempt。派发或恢复有效租约时，同事务将可执行意图推进到 `running`。定义双向约束时同步审计意图撤销、搁置、计划修订及交付复核路径，确保它们不会留下仍可执行的租约。历史状态冲突先呈现于预演结果。

| 最后一个活跃 Attempt 离开时的事实 | 意图与调度结果 |
|---|---|
| 交付报告已提交，Attempt 为 `completed` | 转 `awaiting_review` 或通过既有交付校验后结案。补上完成与复核之间的崩溃窗口。 |
| 执行被显式暂缓 | 进入现有等待路径并保留暂停的 Attempt 和恢复条件。自动派发跳过，显式恢复重新校验。 |
| 租约过期、提供方限流或明确可重试故障 | 累加失败重试计数，设置下一次允许派发时间。预算用尽进入 `blocked` 并搁置。 |
| 协调者明确取消 Attempt 以更换执行者 | 回 `queued`，保留取消原因及旧记录。下一轮由协调者选择执行者。 |
| 明确放弃方向，或记录表明必要条件不满足 | `blocked` 并记录搁置原因、范围、来源及重新考虑条件。显式取消意图的既有语义保留。 |
| 历史原因无法分类，或执行效果为 `unknown` | 保留原文和待核查事项。禁止未经核查重复未知操作。缺失事实交复核，默认搁置等待确认。 |

保留 `recovery_note.reason` 供人阅读，新增受控原因码及必要参数。核对 Worker 的 `provider_error` 和无 completion 收尾。当前两者都可能写成 `cancelled`，新增结构化数据后才能区分限流、执行失败和主动换人。HTTP 429 优先使用有界的 `Retry-After`，否则走本地退避策略。一次连接失败不能推出目标长期不可达。

## 2. 把对账接进写事务

1. 把 `transitionIntent` 的事务内写入提取成共享原语，复用状态校验、历史、版本及 Outbox。新增内部 `reconcileIntentLiveness(tx, ...)`。调用方提供项目、意图、触发 Attempt 和事务边界，函数重读当前状态、有效租约及已保存报告。保留尚有其他活跃 Attempt 的意图。
2. 在 `attempts.mjs` 接入派发、恢复、暂缓、取消、租约清扫和完成事务，核对其他能改变执行权的入口。一个事务原子写入 Attempt、Intent、历史、搁置和通知。禁止在事务内再次调用 `runSerial`。完成路径复用现有交付校验，不能因 Attempt 完成而推定意图已解决。
3. 把租约清扫和项目对账放在运行时读取 workload 之前，先于模型调用和等待短路。事务入口本身具备对账能力。正常写路径覆盖所有 Attempt；周期兜底扫描项目内剩余不一致记录。移除要求 Orchestrator 手动修复孤儿的提示，保留不变量告警。
4. 新迁移持久化 `retry_count` 和下一次可派发时间，以 Attempt 的终态版本为计数去重键。首版建议每个失败周期最多 3 次自动重派，首次失败使用短退避，连续失败延长等待。上限可由项目策略覆盖，且受项目现有预算限制。仅在明确重新激活且条件已变化时开启新周期，历史计数仍可查。

## 3. 让重派、搁置与回溯一致

1. 统一运行时 workload、Orchestrator 候选列表与派发网关的可执行条件。现有 workload 用「从未有 Attempt」过滤意图，回到 `queued` 后仍会被漏掉。改为检查当前状态、活跃租约、退避、搁置及项目状态。真正派发仍重查授权、前提和预算。
2. 从 `shelveBranch` 提取同事务写入原语，保证同一意图同一时刻只有一条活动搁置。搁置保存触发 Attempt、当前目标范围、原因和可验证条件。等待期间由相关变化提供重新考虑信号。现有 `evaluateWakeConditions` 只看事件类型，需进一步校验事件主体、作用范围和搁置水位。普通通知和无关探测结果不能解锁，条件成立后再经现有恢复入口重验。
3. 搁置时给协调面板一个从 Intent 到 Goal 的返回入口，并列出该 Goal 下可派发的兄弟意图及不能派发的原因。当前 Goal 无可执行项时沿 `parent_goal_id` 上浮，区分全部受阻、暂时退避和已完成。对同一阻塞事实合并通知。程序提供候选和停顿原因，由协调者选择后续路线；没有候选及相关变化则等待。

## 4. 回归与存量修复

- 在隔离库复现取消、过期、失败、暂停和正常完成。覆盖剩余另一个活跃 Attempt、迟到回报、完成后复核前崩溃、重复 tick、同时派发与取消。验证提交后零孤儿，历史、计数和事件均只写一次。
- 验证达到重试上限只搁置一次，重启不清零，退避期禁止派发，时间到达可被调度发现，暂停或停止项目不会重新执行。故障注入检查事务整体回滚。
- 验证搁置后返回父 Goal，有可用兄弟时列出候选；无候选时进入等待。无关事件不唤醒。满足条件后恢复时重新检查范围、前提和预算。全程可用本地数据复现。
- 对用户提及的 `0011`、`0013` 先用完整项目 ID、意图 ID 及 Attempt 历史做只读预演，展示旧状态、触发记录、拟转换、是否计数及搁置条件。当前记录未核实，不能预判两条都应重排。用实际数据库副本验证预演结果，正式归位时走同一对账事务并检查状态版本。存量归位与新增网络执行分开验收。
- 合入门禁为 `npm test` 加上述故障与恢复场景。用不调用模型的测试证明对账和幂等成立，再用模拟协调轮次验证回溯候选能被消费。
