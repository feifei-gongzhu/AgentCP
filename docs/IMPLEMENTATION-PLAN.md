## 1. 项目与角色上下文

1. 梳理 `explore`、四角色和运行时的输入。统一供给当前项目任务、项目描述、范围版本和实际规则、资源限制。兼容旧项目空 `task`，使用描述作为目标来源。目标缺失时显式标记。
2. 删除 Worker 中固定项目、范围编号和作业目标。将 Planner 与 Orchestrator 的侦察输入改为当前项目可追溯的候选线索。产品规则仅在证据匹配时适用，调用工具由当前意图决定。
3. 保留派发和执行边界的范围、前提、租约检查。超范围对象可登记为发现，主动执行仍由网关判定。协调者调整意图目标或关键假设时走持久修订或重新规划。

验收用两个任务、两个范围不同的项目捕获角色实际模型输入，验证角色输入随项目切换，旧项目的目标和线索不会串入。验证仅获准读本地文件的任务可规划为资料调查，未获授权的网络动作在网关拒绝。通过后进入阅读协议施工。

## 2. 主动阅读与可达性

1. 基于 `projection.mjs` 和 `records-read.mjs` 增设共享阅读服务。定义资产根、探索根及稳定记录入口。索引节点引用现有对象 ID。目录调整保留旧入口的可达性。
2. 提供打开节点、列子节点、搜索、跟随关系、返回上层和读取证据片段。子节点和搜索支持过滤、稳定排序及游标分页。响应包含所属路径、来源、相关意图、是否还有结果。证据片段返回内容哈希和明确的字节范围或定位信息。
3. 给角色接入同一阅读协议，从精简根入口开始。书签以项目及角色或执行身份隔离，保存当前阅读位置与查询游标。执行意图保持独立。前端用同一记录身份展示导航入口。

验收把关键记录放在首屏之外，预设模型必须先展开或搜索，再沿边打开证据。测试无 ID 的冷启动、分页越界、新记录可见、跨项目隔离和书签重读。工具调用返回材料的范围随本阶段接口一起记录，供阶段 4 使用。

## 3. 自动批量保存

1. 以现有工具网关为执行入口，先做本地 JS 提取适配器。输入绑定不可变 Blob 及其 Capture，输出记录提取器版本、原始输入哈希、运行 ID、意图和 Attempt。把样本内发现的域名、端点等当作候选数据。
2. 按运行和批次稳定编号。原始材料先固定，批次、条目、来源关系和变更事件在同一数据库事务提交。条目记录出处及具体样本，每项可独立引用。重放相同批次回原回执，同一幂等键遇到不同内容时报冲突。
3. 完成时返回批次入口、分类计数和完成状态。中断后保留已提交批次，并区分未完成与结果未知。阅读服务支持按类别搜索及分页。工具保存批次后合并普通通知，条目由 Agent 按需要组织成观察或后续建议。

验收用数百条本地提取结果检查完整性、单项溯源、回执大小与重试幂等。注入提交前和批次间失败，分别验证无半状态及已提交内容可读。验证仅登记新域名时网关仍拒绝未授权的主动执行。

## 4. 覆盖、证据修正与独立复核

1. 在已有阅读日志之上，新增按意图和 Attempt 写入的检查记录。保存材料范围、检查方法、发现入口、未覆盖部分与适用条件。报告可呈现部分检查或未知，并保留未检查材料的入口。
2. 复用 `judgements.mjs` 和 `verification.mjs` 的分层判断与版本检查。允许 Verifier 从 Manifest 定位原始片段，并按策略用受范围约束的工具重新执行必要检查。复核结果保存条件、依据和证据水位。
3. 区分意图在调查某个假设，还是依赖假设成立。修正判断时保留观察和反证，用明确依赖筛选受影响任务。待执行任务重新校验，运行中任务收到相关变化并在下一执行边界重查前提，历史结果可追溯。

验收用同一字符串在代码中出现、随后发现它属于 Mock 配置的例子，检查观察仍在、解释得到修正、独立复核有来源、共享同一资产但无依赖的任务可继续。另测证据变化与确认并发，以及只读取过材料时覆盖记录仍能显示未知。

## 5. 摘要生命周期

1. 为分支记录语义摘要、引用及覆盖的提交边界。程序生成完整子入口、增量提示和当前判断状态。语义摘要负责描述分支内容及不确定性。
2. 以分支为单位合并待刷新变化。按访问需求、重要性和预算刷新，冷分支使用有限后台预算。刷新开始时固定输入水位，发布时仅推进该水位。晚于水位的新增材料继续显示为待纳入摘要。
3. 给 Agent 同时呈现语义摘要与真实入口。关键判断状态即时从记录读取。结构重组经稳定标识和映射保留旧引用。

验收在刷新执行期间追加新条目并修正一个旧判断，验证刷新后新条目仍可直接定位，未汇总状态正确，判断新状态不等待摘要。验证高频写入时不会为每条记录重写祖先摘要。

## 6. 检查点、交接与长期调度

1. 把 `recovery.mjs` 的接手能力接入正常执行和启动。阶段边界持久化当前问题、阅读位置、少量关键依据及版本、活跃假设、未解决变化和下一步。完整历史按需读。接管时对照现状重新检查关键版本及未知工具状态。
2. 把阶段和最终交接接入持久记录与事件去重。共享产物一经提交即可读，交接引用已有记录。Worker 中断时由运行时提供执行状态、已保存产物和最近检查点，并标明尚无结论的部分。
3. 区分普通变化与重要反证、阻塞、越界发现和并行冲突。复用已有事件流、并发限制和协调决定。记录分支搁置的原因、范围和重新考虑的条件。根据相关变化唤醒，等待时保存现场。报告生成与运行状态独立。

验收覆盖未提交最终交接时重启、重复交接与重复事件、旧检查点引用失效、结果未知的操作重试、无变化等待、条件变化唤醒，以及生成报告后继续探索。记录各阶段实际模型调用，检查恢复是否引入无效重跑。

## 7. 贯穿验收与交付

1. 编写单个本地场景串联前六阶段。开场不给出关键域名和证据 ID。Worker 从 `app.js` 批量提取，主动导航发现线索，补充 Mock 反证，在最终交接前注入进程中断。重启后由 Orchestrator 安排接手，Planner 沿索引形成带依据的后续意图。
2. 用可重复的脚本模型检验程序合同与故障时序。单独使用真实模型检验主动导航、引用正确性与继续探索的能力。记录模型与配置、各角色调用和 Token、重复工作次数、证据引用以及中断前后状态。保留多次运行结果。
3. 按 01 号文件第十七章逐项标记通过、失败或待实测，附测试名及记录入口。全部验收项有结果后再评估完成度。

## 每阶段施工顺序

先复现该阶段缺口，再接通正常入口并添加针对性回归。确认新旧项目数据可读、重试行为与项目隔离正确，跑全量门禁后把结果填回计划。新增持久结构使用向前迁移，历史记录的标识和原始证据引用保持稳定。真实模型不可用时保留该项为待实测，已通过的确定性验证照常记录。

### 已知限制与后续

1. **Worker max_steps=6 成本护栏**：完整的"导航→理解→probe→提交证据→提交发现"链路需要更多步数，但加大 max_steps 会显著增加 token 消耗。可考虑 per-role 配置。
2. **导航引导强度**：flash 级别模型倾向于直接行动，对"先导航后执行"的引导响应不足。需要在 Worker 系统提示中强化导航优先的要求，或使用更强的模型（如 deepseek-reasoner）。
3. **429 限流**：mimo-v2.6-pro 端点 RPM 极低（约 1-2 RPM），已为 httpProvider 添加 3 次指数退避重试。
