实现要点（对照施工要求逐条）：

- **Outbox 消费：路由/去重/重试/游标（§14.2）**——投递模型为拉取式：变化页即投递。
  路由=订阅匹配器（关注集命中 / §15.5 邻接扩展 / 强制通知）；去重=consumer_receipts
  复合主键 + applied 事件不再投递 + redelivered 显式标记；重试=至少一次语义（未确认
  事件可重投，outbox.delivery_attempts 计数、pending→sent 状态推进，供 §20.2 观测）；
  游标=订阅行 last_cursor（仅 applied 确认推进、只前进）+ 变化页 next_cursor。
- **变化页四元组（§14.3）**——events / next_cursor / high_watermark / has_more；
  next_cursor 覆盖已扫描区间（被过滤/已应用事件一并越过但不跳过未扫描内容）；
  页上限截断时游标停在第 limit 个匹配事件，溢出匹配留待下页重扫，绝不越过未投递的
  匹配事件推进；扫描上限 5000 事件/页（资源保障）。
- **游标过期 → CURSOR_EXPIRED + 重同步（§14.3）**——游标 token `c:<订阅号>:<订阅版本>:
  <commit_seq>:<event_index>`；订阅规则显式变化或快照边界更新推进 subscription_revision
  → 旧版本游标一律 CURSOR_EXPIRED，next_requirements 指明「取得新快照及边界后续读，
  跳过区间由新快照内容覆盖」；另有 commit_seq 粒度的事件保留底线检查（首版不清理
  outbox 故不触发，启用清理后自动生效，为真实守卫非装饰）。
- **delivered ≠ applied 分存（§14.2/§14.3）**——delivered 由服务端在变化页**同一事务**内
  写入（投递是服务端事实）；applied 仅经 POST /consumer-acks 由消费者在保存处理结果后
  确认（模型消费者合同：以已保存的计划/执行结果为前提，阶段 E 调用方遵守，本端点只
  持久化回执并校验前提，不替 AI 判断「已处理」）；批确认响应列明覆盖事件集合与连续
  消费边界；同 (consumer, revision, event) 回执唯一，applied 升级覆盖 delivered，重复
  确认幂等（already_applied 计数、游标不回退）。
- **不跳过未处理事件推进（§14.3）**——双前提校验：ack 边界不得越过订阅已扫描区间
  （scan_through，服务端只对已读区间签发可确认边界）；ack 事件必须是已投递事件。
  服务端签发的游标链以快照边界为根、逐页连续，客户端无法凭空构造越过未读区间的
  合法确认。
- **动态订阅随新边扩展（§15.5）**——关注集 = 种子（subject_ids ∪ intent_id）∪ 动态扩展
  （relation.added 命中时并入两端点，随页事务持久化、**不**推进订阅版本——自动扩展不是
  消费者侧规则变化，不触发重同步）；与关注集成员有允许类型未撤回边相连的节点事件直接
  命中（新资产经新边关联已关注节点时不被过滤，即使尚未进入旧子图；判定读当前库内边，
  同批先发现后连边的提交序也覆盖）；批内两遍判定处理批内链式新边并按位置归位。
- **强制通知（§15.5）**——`scope.revised`（范围收缩）、`dependency.changed`（前提撤回/
  requires 变化）、`resource_state.changed`（用户停止/资源与执行状态）无视 focus.
  event_types 过滤投递给项目内全部订阅。执行取消的专属事件类型尚不在蓝图 §6 目录
  （协调项 2），C2 落地时建议复用 resource_state.changed / dependency.changed 或走蓝图变更。
- **订阅边界（§15.2）**——openSubscriptionBoundary 在 runSerial 一致读视图内取
  projects.next_commit_seq 为边界（该事务前全部已提交事件的 commit_seq 均小于它，
  无「先读图再订阅」间隙）；同 focus+scope（规范化内容摘要）更新既有订阅并推进版本，
  异内容建立新订阅。会话路径（POST /subscriptions）同语义。

## 5. 偏差与已知问题

1. **内部状态存放于 subscriptions.focus 保留键 `_sorne_state`（未新增迁移）**：冻结 DDL
   的 subscriptions 表无扫描区间/种子/扩展集列。选择在 focus JSON 附加保留键（边界序号、
   扫描区间、种子与动态扩展集）而非新增 0003 迁移：避免并行期 schema 演进协调成本，
   对外视图与 B1 传入 focus 一律剥离该键；若后续评审要求物化列，走 §12.5 变更流程。
   （未报批——不影响冻结 DDL 与既有表语义。）
2. **执行取消的强制通知映射（协调项）**：§15.5 列举「范围收缩、前提撤回、执行取消」，
   蓝图 §6 事件目录无执行取消专属类型。本模块将 `resource_state.changed` 全类强制
   （含 A1 的用户停止 payload.kind=project_lifecycle，及未来的执行取消若复用该类型），
   并将 `dependency.changed` 全类强制。C2 施工执行取消事件时若新增类型，需同步
   FORCED_EVENT_TYPES（蓝图 §6 目录遗漏 relation.added 已由 A1 上报，同源问题）。
3. **deliveries 的全局 delivery_status 语义**：outbox.delivery_status/pending 为**任一
   消费者**投递即转 sent（全局最早投递视角），各消费者的真实进度在 consumer_receipts
   与订阅 last_cursor。供 /health 与 F2 指标使用时按此解释。
4. **游标 token 内嵌订阅版本**：§14.3 允许「(commit_seq, event_index) 或等价不透明
   token」；本实现把订阅号+版本并入 token，使「规则变化→游标过期」判定精确到版本、
   无需额外服务端状态。客户端不得解析 token 内部结构（视为不透明）。
5. **B1 openSubscriptionBoundary 的 consumer 归属**：§2.7 签名无 consumer 参数；
   B1 经 focus.consumer_id 指定消费者（缺省用 `boundary-<key12>` 合成消费者，仅可读

## 6. 留给后续阶段的接口预留

- 阶段 E（E1/E2）：消费确认的「已处理」合同——模型消费者须在协调决定/汇报处理结果
  **持久化之后**才以对应边界/event_ids 调用 POST /consumer-acks；Orchestrator 工作面板
  可按 consumer_receipts 的 delivered-but-not-applied 差集呈现「已投递未处理」积压。

  `dependency.changed`（见偏差 2）；runtime 角色可建订阅并为本消费者 ack。
- F2（运行观测）：Outbox 积压（pending 计数）、重试（delivery_attempts 分布）、
  订阅滞后（high_watermark − last_cursor）、delivered≠applied 差集均可从
  outbox/consumer_receipts/subscriptions 直接观测。
