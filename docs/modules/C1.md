### 计划接收的四类检查（§16.2）

1. **对象存在**：goal_id→goals、target_asset_ids→assets、basis_refs/prerequisite_refs→
   任意业务表（多态定位）；计划内 local_ref 预留编号可前向引用（条目顺序不限）；
   不存在 → INVALID_REFERENCE 整单回滚（真实事务验证：无意图/无计划行/无新事件/
   无回执，commit_seq 不留消费）。
2. **范围有效**：计划级/意图级 scope_revision 必须存在于本项目（输入兼容版本标签
   "1" 与范围行编号 "SR-…"，统一存行编号）；都未声明时回落项目当前范围；项目从未
   配置范围 → SCOPE_UNRESOLVED。目标资产 `scope_status=denied` → 仅该意图条目级拒绝
   （SCOPE_DENIED）；pending 只告警（派发与工具执行前的逐跳范围校验属 C2 §17）。
3. **前提版本有效**：plan 级 `prerequisites[]` 声明 `{ref, expected_state_version/
   expected_status/expected_review/expected_claim_revision/expected_evidence_revision/
   expected_assessment_epoch}`（按目标表可用字段校验，不适用 → BAD_REQUEST）。
   失效前提只影响引用它的意图：默认**挂起**（落库为 blocked + 理由 + 恢复条件
   `resume_conditions[{kind:prerequisite, ref, description}]` + intent.blocked 事件），
   或按意图声明 `on_prerequisite_invalid:"reject"` 拒绝该条目；其余意图照常接收，
   received_status=partial/suspended/rejected。**无关新增不使计划失效**（§16.2 句末，
   §20.3 场景 10 语义）：只有被声明前提自身的版本/状态变化才触发分流，全局
   commit_seq 推进不影响。
4. **依赖死锁**：调度前提图（intent→intent 的 requires 语义 = prerequisite_refs ∪
   未撤回 requires 边；探索血缘与弱关联不参与）成环 → DEPENDENCY_CYCLE 整单回滚
   （含同计划互为前提、自引用、跨计划修订闭合环路三类；三色 DFS 带 visited 与
   节点/边规模上限）。

其他语义：完全相同提交按幂等规则返回原回执（submissions 表身份域
(project,submitter=planner actor,submission_id) + 请求摘要）；疑似语义重复（同问题
同类型未结意图）只告警「交 AI 判断，程序不强制合并」（§16.2/§6.3 无相似性唯一键）；
revise 为 §11.3 修改型（expected_state_version），终态意图拒修订（resolved 只表示该
版本问题已处理，新问题建新意图引用旧意图）；修订换前提时计划来源 requires 边收缩
（撤回边发 dependency.changed superseded）；修订把前提全部换有效时 blocked 意图随
修订解除挂起（§9.2 重评估不一律改失败）。

### 完成建议的程序检查（§10.1「一句完成不关项目」）

- 状态条件：意图必须 running/awaiting_review；requires 边上记录的前提期望此刻重验
  （§2.9/§9.2 动作前重查必要前提），失效 → PRECONDITION_INVALID + 恢复条件。
- 必要产物：声明的每个交付物须有证明（`deliverables_proof[{index|key, record_ids}]`），
  证明引用的记录必须真实存在（伪产物 → INVALID_REFERENCE）；缺失 → 422 列出缺口，
  意图保持原状态。
- 未声明交付物的完成建议无法程序验证 → 只进入 awaiting_review 交 planner/verifier
  复核（语义争议交 AI），复核后经 resolve 转换。
- resolved 只表示该版本问题已处理：**不触碰项目状态**（用例断言 project.status 不变、
  其余意图不动、后续计划仍可接收）。
