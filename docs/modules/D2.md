### §2.7 冻结签名（本模块为唯一实现方）

`applyStateTransition(db, { project_id, subject_kind, subject_id, expected, action,
verification_result_id })` 导出于 `lib/store/judgements.mjs`：

- **§8.4 状态转换合同的唯一实现**（全系统仅此一套状态机；D1 的 §12.2 核心事务在完成
  身份/Manifest/版本校验后调用，D1 已按本词表装配：confirm / falsify /
  mark_insufficient / mark_conflicting / require_review / reopen + hypothesis 的
  test/support/reject/mark_inconclusive + fact 的 dispute/supersede/retract）；
- 前提校验按 §8.4 表逐行：应用型转换必须携带 `verification_result_id` 且 outcome 匹配、
  必要检查（checks 显式 failed/not_met 项）通过、**发现者 ≠ 验证结果提交者**（蓝图
  §8.3.2）、版本四元组匹配（state_version→STALE_STATE、claim_revision/
  assessment_epoch→CLAIM_CHANGED、evidence_revision→STALE_EVIDENCE，§12.3 情形 1）、
  confirmed→falsified 需显式 `overturn:true`（「明确推翻历史判断，而非仅本次未复现」
  的程序化声明）、falsified→reopen 推进 assessment_epoch 开新验证不直接确认；
- mark_insufficient 三分流（§8.4 末段）：未确认→inconclusive 不伪装已排除；confirmed
  保持并置 review=pending（补验不足不自动证伪原结论）；falsified 不动；
- 在调用方事务内同步执行（不自行开事务），事件结构返回给调用方在其事务内 flush
  （`opts.emit` 提供时同时送入）——漏洞发 `vulnerability.state_changed`（确认/修正
  事件），推翻/失效追发 `judgement.invalidated`，影响 requires 前提的转换追发
  `dependency.changed`（受影响边与依赖方入 payload，§8.2/§9.2）；
- 受理但无字段变化的转换如实返回 `changed_fields: []`，不虚增版本。

### 资产身份与分层去重（§7.1/§7.2/§7.3，`lib/store/dedup.mjs`）

- 纯函数：`canonicalizeServiceIdentity`（CANONICALIZATION_VERSION=`service-identity-v1`：
  scheme/host 大小写统一、显式默认端口视为等价省略、非 ASCII 主机保留原样不做 IDNA
  推断、IPv6 字面量保留独立身份）、`canonicalizeHttpResource`（url_exact 恒为原始串；
  路径大小写/编码原样、查询串顺序与重复参数原样、fragment 不属资源身份）、
  `derivePathTemplate`（TEMPLATE_RULE_VERSION=`path-template-v1`：数字/UUID/Hash 段折叠
  {n}/{uuid}/{hash}，其余段原样保留）；
- submission 操作（经 A1 `registerSubmissionOps` 扩展点注册，不改其文件）：
  - `register_service_asset`（append/worker）：版本化规范化建服务资产，original_input
    保留首见原始输入不被后续等价输入覆盖，等价身份经 UNIQUE 约束归并（并发不先查后插）；
  - `register_http_resource`（append/worker）：精确资源样本（method+url_exact 唯一键），
    参数组合不因资产合并丢失，重复登记去重警告不产生重复样本行；
  - `observe_resolution`（append/worker）：域名与 IP 各自成独立资产节点 +
    related_to 边（conditions.kind=dns_resolution）——不自动合成一个资产；
  - `propose_endpoint_template`（append/worker）：样本推导候选模板（一次一个模板，多
    模板/多 method 拒绝），template_members 保留 captured_from 样本来源；
  - `revise_endpoint_template`（modify/worker）：confirm/withdraw/split——拆分把成员
    重挂新模板并保留 captured_from，resources 样本行永不删除；expected_state_version
    校验（STALE_STATE）；
  - `merge_candidate_group`（modify/worker）：group_key（asset+location+category）只用于
    查找聚合——建组 + memberships + duplicate_of/equivalent_to 显式关系（原 ID/引用/
    证据全部保留，不删除被合并节点）；组已存在时 expected_group_state_version 校验；
  - `split_candidate_group`（modify/worker）：误合并可拆分——成员移出 + 组内合并边
    撤回（retracted_at 留历史），漏洞行绝不动；组清空自动 closed。

## 5. 偏差与已知问题

1. **新增事件类型 `judgement.state_changed`**：蓝图 §6 目录无假设/事实/模板/候选组
   状态变化事件（vulnerability 有专用类型，其余判断类对象没有）。规范 §14.1 必要事件
   含「判断失效」（judgement.invalidated 已覆盖）但状态/复核变化无对应类型，§8.2 状态
   表又要求可观察更新。未改蓝图，上报目录遗漏（A1 relation.added 同源问题）。
2. **applyStateTransition 的可选扩展字段**：冻结签名两参之外，`emit/actor/now/
   commitSeq/overturn/reason` 以可选字段并入参数对象读取（不传即安全缺省；D1 按冻结
   签名两参调用完全兼容——其已落地的装配与词表实测对齐）。`overturn` 是 §8.4「新验证
   明确推翻历史判断，而非仅本次未复现」区分语义的程序化显式声明（程序无法从结果
   语义判断「推翻 vs 未复现」，只能要求调用方显式声明）。签名兼容性解释，未报批。
3. **错误码超出 §2.7 所列三码**：STALE_EVIDENCE（证据集版本不匹配，§5.3 注册表内）、
   INVALID_REFERENCE（对象不存在）、BAD_REQUEST（未知动作）——均为既有注册表码，未
   扩表；§2.7 文字列举的 STALE_STATE/CLAIM_CHANGED/PRECONDITION_INVALID 语义不变。
4. **record_fact 角色 = verifier**：蓝图 §8.2 矩阵 worker 操作集不含 Fact（漏洞判断
   不得借 Fact 绕过验证的角色面），verifier 行「verification 结果提交」扩展为「核实
   归档」；`versioned_rule` 通道（§8.1「经过相应规则……核实」）只校验 rule_id/
   rule_version 可追溯，不校验规则执行真伪（程序不能假冒规则已执行，也不能阻止版本化
   规则通道——规则引擎属 D/F 阶段）。语义边界上报评审。
5. **编号带项目前缀**（`A-/RES-/T-/CG-/M-/R-/F-<projectId>-NNNN`）：规避 C1 偏差 6
   实证的 A1 跨项目主键冲突（同库第二项目 SR/R 编号 UNIQUE 冲突）。复合前缀不经 A1
   locateRecord 前缀解析：assets/facts 在其 fallback 扫描表内可解析；resources/
   endpoint_templates/candidate_groups 不在，D2 操作内部自行校验存在性（模板/组编号
   目前仅 D2 域内引用；如后续模块需经 /records 或 add_relation 引用它们，需扩展
   解析表或走 §12.5 变更流程）。
6. **操作回执只透传主 id**（A1 引擎契约 accepted_operations[].id）：多编号结果
   （observe_resolution 的 IP 资产/解析边、模板拆分的新模板编号）经 warnings 文本与
   事件 payload 携带，不扩展 A1 回执结构；测试以库断言核对真实行为。
7. **hypothesis/fact 状态机并入 applyStateTransition**：§8.4 合同表只列漏洞转换，
   §8.2 状态表对假设/事实另有「根据执行与验证结果更新」「验证服务与受控修正流程」的
   状态控制行——按「全系统仅一套状态机」的模块要点参数化到三类 subject（同一
   TRANSITIONS 表、同一前提校验、同一事件语义）。D1 落地的 TRANSITION_ACTIONS 词表
   已按此对齐（hypothesis: support/reject；fact: 验证不直接驱动、经受控修正）。合同表
   扩展，供评审确认。
8. **漏洞状态历史无专用表**：§8.2「可以保留历史状态」为建议级（§10.1 意图历史是
   「必须」级、C1 建表先例）；本模块以持久 outbox 事件（from/to/reason）+
