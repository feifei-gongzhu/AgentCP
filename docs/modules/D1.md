  - **#28 POST /sorne/verification-results**：§12.2 核心事务——校验（验证身份/判断版本/策略/Manifest/引用/检查项覆盖/发现者不自证）→ 保存不可变 VerificationResult → 同一 runSerial 事务内读 subject 三版本 → 全部匹配且必需检查通过才经 §2.7 `applyStateTransition`（D2 唯一实现）应用 → 同事务 Outbox（`verification.completed` 含未应用意见 + D2 返回的状态/依赖/失效事件）；版本竞争分支事务提交后以 STALE_EVIDENCE / STALE_STATE / CLAIM_CHANGED 错误信封**带回执**返回（§20.1 不用错误掩盖提交已成功）；同 job 同内容重发返回原回执（传输级幂等）
  - **#29 GET /sorne/verification-jobs**：验证队列视图（Manifest 摘要/期望版本/等待时长/最新结果 outcome），状态与 outcome 过滤、created_seq:id 游标分页、会话项目域校验（跨项目拒绝）
- 表/迁移：`verification_jobs`、`verification_results`、`evidence_manifests`（§12.1 不可变清单：成员/条件/判断版本/策略版本/content_hash，UNIQUE(project,subject,evidence_revision,claim_revision,policy_version) 即不可变锚）、`evidence_memberships`（只读投影）；**未新增迁移**（冻结 DDL 足够）

- 事件：`verification.completed`（含未应用意见、decision、review 前后值）；D2 转换返回的 `dependency.changed`/`judgement.invalidated`/`vulnerability.state_changed`/`judgement.state_changed` 由 D1 并入同事务 Outbox

## 3. 验证

- 新增测试文件与用例清单：`test/verification.test.mjs`，32 用例：
  1. §8.3 五要素齐备：创建 pending 任务并绑定不可变 Manifest 与期望三版本
  2. §8.3 五要素缺失或非法分别拒绝（不创建任务）
  3. §7.3 去重键四成分：同键同任务；新证据/新条件/新策略版本 → 新任务（续验通道）
  4. 请求角色面（worker/orchestrator/verifier 可发起；user/planner/runtime/无会话拒绝）
  5. 声明一致性：未声明反对证据但库内存在 active 反对成员 → 告警并全列 Manifest
  6. Manifest 不可变（§12.1）：同键幂等返回同一 id 与 content_hash
  7. Manifest 按证据集版本生成：新证据 → 新 Manifest，旧行不变
  8. §8.3(1) 仅 verifier 会话可交结果（其余角色/无会话 403 且无落库）
  9. §8.3(2) 发现者不得自证：supported/falsified → 403 无落库；insufficient（非应用型）允许且不得升级判断
  10. §12.1/§12.2 步骤 1：错 Manifest / 错 reviewed_evidence_revision / 错策略版本 / 错 claim 回执分别拒绝

  12. §12.2 应用：supported+匹配+检查通过 → confirmed、state_version 推进、review=clear、事件同事务
  13. §8.4 falsified：明确排除当前判断；证据与采集历史保留
  14. §8.4 conflicting：review=disputed，结论状态不被覆盖
  15. §8.4 insufficient：未确认问题可为 inconclusive（D2 mark_insufficient 动态分流），缺口保留
  16. 再确认路径：对已 confirmed 的 supported 复核意见保留但不重复转换（no_transition）
  17. §8.4 confirmed→falsified 需显式推翻声明（overturn）：缺 → 拒绝；携带 → 应用并保留历史

## 5. 偏差与已知问题

- **D2 并行落地与 action 词表（协调项，请架构师追认）**：D2 于本窗口中途（2026-11-05 09:29 起落地，12:51 仍在更新）交付 `applyStateTransition`。蓝图 §2.7 冻结了签名但未冻结 action 取值；D1 的 outcome→action 路由表按 D2 落地实装绑定（vulnerabilities: supported→confirm / falsified→falsify / conflicting→mark_conflicting / insufficient→mark_insufficient；hypotheses: supported→support / falsified→reject；facts: 验证路径不驱动转换）。D2 未落地窗口经 `__installStateTransitionForTests` 安装测试文件内的真实事务实现承载（B1 先例）；D2 落地后所有应用用例走其真实默认装配（集成用例实跑非跳过）。词表已在 D1 模块头文档化。
- **§12.2 事务顺序适配 D2 落地版契约**：D2 的 `applyStateTransition` 按 `verification_result_id` 回读结果行并返回事件结构（不自行写 Outbox）→ D1 顺序为「先落不可变结果行（applied=0）→ 调用状态机 → 应用成功置 applied=1 → D2 返回事件并入同事务 Outbox」。版本竞争分支在事务提交后以错误信封带回执返回（§20.1）。D2 抛 overturn_guard（confirmed→falsified 需显式推翻声明）时按前提校验失败整体拒绝不落库（verifier 携带 `overturn:true` 重交，测试 17 双向验证）；§8.4 起点不被合同接受时（如对已 confirmed 再 confirm）D1 捕获 D2 结构化 from 状态错误（extra.detail.allowed_from）降级为 `no_transition` 保留意见（测试 16），不丢弃验证意见也不另行实现状态机。
- **版本不匹配分支的复核标记分工**：证据基线/判断核心移动时 D1 按 §12.2「标记需复核」置 review=pending（仅 vulnerabilities、仅 clear→pending 单向）；subject 已 confirmed 时经 D2 `require_review` 动作（附带受影响依赖枚举事件）；**state_version 单独移动（如另一验证已应用）不置复核**——§12.3 情形 3「不制造虚假冲突」与 §16.3「确认漏洞可立即产生后续方向」的反向保障（测试 26 断言并发落败方不污染复核）。
