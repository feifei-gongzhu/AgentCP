### 2.1 §19 逐条落实

| §19 要求 | 落实 |
|---|---|
| 漏洞报告自 suspected 起即可形成草稿 | 每个漏洞在报告视图首次读取时建 v1 草稿（`syncVulnerabilityReports`），内容为该时刻全部结构化事实 |
| 状态、证据、条件和影响持续更新 | 报告相关指纹（状态/复核/条件/影响/证据集成员/验证结论/来源与后续引用）变化 → 切新版本；指纹剔除 `data_boundary`/`version_record` 记录性字段，其他对象的提交不增殖本报告版本（§20.3 场景 10 报告面） |
| 确认后生成对应确认版本 | confirmed 状态变化切新版本，携带 `confirmed_version`（验证结果编号/判断版本/确认时间）与验证结论（applied=true） |
| 被排除或争议时同步当前视图，历史版本保留 | falsified / review=disputed 同步新版本；全部历史版本行+文件保留，`?version=vN` 可读回；`history` 随单份报告返回 |
| 报告至少包含：漏洞 ID、资产、状态与复核状态、判断条件、支持/反对证据、验证结论、限制、来源意图和后续意图 | `subject`（含资产身份块/条件/状态/复核/三版本）、`supporting_evidence`/`opposing_evidence`/`historical_evidence_members`（撤回/争议成员保留呈现，§2.8）、`verification_conclusions`（results+pending_jobs）、`limitations`（验证限制+规范语义限制：confirmed≠持续存在、排除≠历史上不存在、未注明条件不可推广、复核非 clear 警示、suspected 不得作确认前提）、`source_intents`、`follow_up_intents` |
| 阶段报告注明数据截止版本和时间 | `data_boundary.snapshot_commit_seq`（= 生成时一致读视图内最后已分配 commit_seq）+ `generated_at`，行 `data_boundary` 列同存 |
| 已确认成果/未确认线索/已完成方向/受阻方向及未覆盖部分 | milestone 五块 `confirmed_findings`/`unconfirmed_leads`/`completed_directions`/`blocked_directions`/`uncovered` + `exploration_continues`（进行中意图计数与「生成后探索继续」说明） |
| 覆盖度不能简化成「资产挂过一个 Fact 就已测」；按资产/功能/测试方向/身份或条件的完成情况记录 | `coverage.records` 按资产：四类测试方向（collect/investigate/verify/revisit）各自 total/resolved/blocked/ongoing 计数、采集与观察计数、身份条件双清单（意图声明的要求 vs 采集观察实际出现的条件）、发现计数、`uncovered_flags`（no_direction/no_capture）；常驻 `coverage_note` 明示「已执行过某方向不代表该资产没有其他漏洞」 |
| 报告是持续探索的产物和引用入口，生成后探索继续 | 报告生成零业务副作用（不改项目状态/意图/漏洞）；`exploration_continues` 呈现在途探索；场景 22 配合面用例断言报告与确认后项目仍 active、planner 可继续安排后续方向 |
| （§21 F）任何漏洞/事实可四向追溯来源/执行/证据/后续方向 | `buildSubjectTrace` 通用追溯构建：来源（discovered_from/derived_from 边，无边时显式「不推断」+持久溯源字段）、执行（证据采集归因 attempt_id + produced_by 边 → Attempt 与工具调用六态汇总）、证据（证据集成员下钻至观察语句→采集→Blob sha256/表示形式 + supports/contradicts 边含撤回标记 + #43/#44 读取入口）、后续方向（basis_refs/prerequisite_refs 引用意图、requires 下游边、验证建议）；漏洞报告全量携带，事实经阶段报告 `confirmed_findings.facts[].trace` 携带 |

### 2.2 写入顺序与一致性（§13 同法）

一致读视图（BEGIN DEFERRED 同步读，B1 同法）内取内容 → 原子写文件（tmp+rename）→
`runSerial` 落 `report_revisions` 行：库行不引用未固定文件；行插入失败留下孤立文件，
由下次同步以同版本号回收（用例 17 以真实 TRIGGER RAISE 注入验证：无半行、旧版本
完好、恢复后同号回收）。同步与生成不改任何业务对象状态。

## 5. 偏差与已知问题

1. **报告版本同步为读取时惰性同步（映射决策，未报批）**：规范 §19「自 suspected 起
   即可形成草稿」——F1 落地为「报告视图首次读取时建草稿；此后每次读取把当前视图
   同步到最新版本」。未在漏洞创建事务内挂钩草稿生成（D2/A1 的写入路径不归本模块，
   §2.7 无对应冻结签名）；效果等价（任意时刻读取都保证草稿与当前版本在场），但
   「从未被读取过的漏洞」在库中无报告行。供评审确认是否需要事件驱动挂钩。
2. **报告版本生成不发 Outbox 事件**：蓝图 §6 目录无 report.* 类型（A1 已上报的目录
   遗漏问题族）；按 B1 快照先例作纯派生资料处理。若评审要求报告生成通知（如 F3 页面
   刷新），需扩目录并走 §12.5。
