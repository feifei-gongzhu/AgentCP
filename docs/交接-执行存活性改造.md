## 1. 要解决的问题（一个根因，三种表现）

用户看到的「悖论」：worker 已取消，意图却仍显示「执行中」。本质是**执行健康状态只活在日志/内存里，没有落成可对账的持久事实**，于是出现三种表现：

1. **孤儿意图**：取消/中断某个 attempt，从不回写它所属 intent 的状态 → intent 永远停在 running。
2. **模型崩溃不恢复**：provider 出错后没有持久健康记录 + 指纹在调用前就写了 → 恢复后被永久跳过。
3. **UI 说谎**：诊断只看「是否配置」，不看「是否真的可达」→ 配了就显示「正常」。

## 2. 原理（两篇论文）

- **MemWalker**：树要能确定性回溯——分支走不通就回到父节点，不靠猜。
- **PentestGPT PTT**：每个节点的状态是执行历史的**确定性函数**，每步由控制器回写，保持自洽。

落到本系统一条不变式：

> **intent 处于 running ⟺ 至少有一个 active（leased/running）的 attempt。**

任何破坏这条不变式的地方，都由一个确定性对账函数拉回，而不是交给 LLM 去「记得处理」。

## 3. 三类 reason_code（从 GPT 的 6 类砍到 3 类）

attempt 结束时必须带一个 reason_code，决定 intent 怎么走：

| reason_code | 含义 | intent 动作 |
|---|---|---|
| `retryable` | 超时 / 429 / 5xx / 中断 / 租约过期 | requeue（回 queued），**不消耗方向失败预算** |
| `reassign` | 显式取消以换 worker | requeue（回 queued） |
| `dead_end` | 方向被放弃 / 前置条件不满足 | block + branch_shelving（搁置分支） |
